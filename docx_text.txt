1. Introduction
1.1 Background of the Application Domain
Modern urban environments are increasingly challenged by severe traffic congestion driven by rising vehicle density and the limitations of traditional, static traffic control infrastructure. Fixed-cycle traffic signals and pre-planned routing systems are inherently unable to adapt to the dynamic, real-time fluctuations that characterize actual road networks. The direct consequences include increased travel times, higher fuel consumption, greater emissions, and degraded urban productivity.
Graph theory provides the mathematical backbone for modeling road networks as weighted directed graphs, where intersections become nodes and road segments become edges carrying capacity and flow attributes. The discipline of algorithmic optimization — particularly shortest-path computation via Dijkstra’s algorithm — gives rise to systems that can compute, in real time, the least-cost path for any vehicle given current congestion levels. When coupled with queue-based intersection models and adaptive signal control strategies, the result is a simulation framework that closely approximates real-world intelligent transportation systems.
1.2 Brief System Overview
The Adaptive Traffic Flow Optimization System models a city road network as a directed graph and simulates multi-vehicle traffic over discrete time steps. At each simulation tick, vehicle flows are updated, road congestion and travel times are recalculated using the Bureau of Public Roads (BPR) formula, optimal routes are recomputed via Dijkstra’s algorithm, and traffic signals are adaptively adjusted by granting green time to the intersection approach with the longest queue. The system is implemented in C++ and rendered in real time using the Raylib graphics library.
2. Problem Statement
2.1 Clear Definition of the Problem
Urban road networks exhibit time-varying, non-linear traffic behavior that cannot be managed effectively by static control policies. The core problem is: given a directed road network with defined capacities and speed limits, a stream of vehicles with distinct sources and destinations, and an objective to minimize total network congestion and travel delay, how can a software system dynamically compute optimal vehicle routes and adaptively control intersection signals to achieve near-optimal throughput?
Formally, the network is represented as G = (V, E), where V is the set of intersections and E is the set of directed road segments. Each edge eij carries parameters including road length lij, maximum speed vij_max, capacity cij, current flow fij(t), downstream queue Qij(t), and congestion-adjusted travel time wij(t). The system must simultaneously route N vehicles across K source-destination pairs while minimizing the global objective function that balances queue lengths and congestion ratios.
2.2 Limitations of Existing Approaches
Static traffic signals use fixed phase durations regardless of real-time queue lengths, causing unnecessary delay on low-traffic approaches while congested approaches remain blocked.
Pre-planned routing assigns vehicles to fixed paths computed at departure and does not react to en-route congestion, systematically overloading initially uncongested roads.
Simple graph-based shortest-path implementations ignore flow dynamics and compute routes based on free-flow travel times rather than current traffic states.
Existing simulators either oversimplify the traffic model (ignoring queuing and capacity constraints) or are too computationally expensive for real-time interactive simulation.
3. Objectives
3.1 Primary Objective
To design and implement a fully functional, modular C++ simulation of an urban traffic network that combines graph-theoretic road modeling, congestion-aware Dijkstra routing, queue-based intersection dynamics, and adaptive traffic signal control — fulfilling the Complex Engineering Problem requirements of the EC-200 Data Structures course.
3.2 Secondary Objectives
Implement a directed weighted graph class to represent the road network with adjacency-list storage for O(1) neighbor lookup.
Implement the BPR (Bureau of Public Roads) travel-time model to dynamically update edge weights based on real-time congestion ratios.
Implement Dijkstra’s algorithm with a priority queue (min-heap) to compute optimal vehicle routes in O((V + E) log V) time.
Implement a queue-based intersection model that tracks Qij(t) per incoming road and discharges vehicles based on signal state, discharge rate, and downstream capacity.
Implement an adaptive traffic signal controller granting green to the maximum-queue incoming road at each intersection, with configurable green duration Tg.
Implement a Vehicle class modeling per-vehicle state, decrementing remaining travel time each tick, and triggering rerouting upon segment completion.
Implement a PerformanceMetrics module tracking average travel time, total delay, throughput, and average network congestion level.
Develop a real-time Raylib-based graphical interface rendering the road network, vehicle positions, signal states, and a congestion heat map.
3.3 System Overview
The simulation operates as a discrete-time loop. Each tick executes five ordered phases: (1) vehicle flow and queue updates, (2) congestion ratio and travel-time recalculation, (3) Dijkstra rerouting for vehicles completing a segment, (4) adaptive signal state updates, and (5) performance metric accumulation. This architecture mirrors the real-time control loop of deployed intelligent transport systems while remaining computationally tractable for a single-machine C++ implementation.

4.2 Inter-Module Communication
The SimulationEngine holds direct references to the RoadNetwork, the Vehicle vector, and the PerformanceMetrics instance. Each simulation tick, it calls Road::updateCongestion(), then Dijkstra::computePath() for vehicles completing a segment, then TrafficSignal::updateSignals() on all intersections, then Vehicle::tick() on all active vehicles. The flow is strictly sequential within each tick to ensure data consistency.
4.3 Key Design Decisions
Adjacency list over adjacency matrix: Sparse urban graphs (low average degree) make list storage significantly more memory-efficient and faster to traverse.
Lazy Dijkstra with stale-entry removal: Vehicles are only re-routed when they complete a road segment, avoiding O((V+E)logV) computation every tick.
Max-queue signal policy: Granting green to the longest-queue incoming road approximates the optimal single-intersection control policy without requiring global optimization.
BPR travel time: The Bureau of Public Roads nonlinear formula (α=0.15, β=4 by default) provides a well-validated congestion response curve used in real traffic engineering.

5. Mathematical Modelling
5.1 Road Network Model
The road network is represented as a directed graph:
G = (V, E)
where V is the set of intersection nodes and E is the set of directed road edges. Each edge eij from node i to j carries: length lij, maximum speed vij_max, capacity cij, current flow fij(t), downstream queue Qij(t), and congestion-adjusted travel time wij(t).
5.2 Traffic Flow Update
Vehicle flow on each road evolves per time step as:
fij(t+1) = fij(t) + aij(t) − xij(t)
where aij(t) is the number of vehicles entering edge eij at time t, and xij(t) is the number leaving eij into the downstream queue. The queue evolves as:
Qij(t+1) = Qij(t) + xij(t) − dij(t)
where dij(t) is the discharge rate, governed by:
dij(t) = gij(t) × min( Qij(t), μij, cjk − fjk(t) )
The three terms enforce: signal permission gij, saturation flow rate μij, and available downstream capacity.
5.3 Congestion Model
ρij = fij / cij
A ratio near 0 indicates a free road; near 1 indicates full congestion.
5.4 BPR Travel Time Model
wij(t) = wij_free × ( 1 + α × (fij(t) / cij)^β )
wij_free = lij / vij_max
Default parameters: α = 0.15 (congestion sensitivity), β = 4 (nonlinearity exponent).
5.5 Shortest-Path Routing (Dijkstra)
Pv = argmin ∑ wij(t)   along path from sv to dv
Edge cost equals current travel time: cost(eij) = wij(t). Dijkstra’s algorithm computes this in O((V + E) log V) using a min-heap.
5.6 Adaptive Traffic Signal Model
∑ gij(t) = 1    for all (i,j) ∈ In(j)
gij(t) = 1   iff   Qij(t) = max over all (i,j) ∈ In(j)
Only one incoming road at an intersection receives a green signal at any tick.
5.7 Global Objective Function
min ∑t ∑(i,j)  [ α×Qij(t) + β×(fij(t)/cij)² ]
This jointly penalizes queue length (waiting time) and squared congestion ratio (road overload).

6.3 Key Implementation Decisions
The priority queue in Dijkstra uses std::priority_queue<pair<double,int>, vector<...>, greater<>> for O(log V) extract-min.
Vehicle rerouting is deferred to segment completion events to avoid redundant Dijkstra calls every tick.
The simulation tick rate is configurable; Raylib’s SetTargetFPS() synchronizes rendering to the simulation speed.
Input validation rejects negative capacities, zero speed limits, and self-loop edges during graph construction.
All dynamic allocations use smart pointers (unique_ptr / shared_ptr) to prevent memory leaks.

9. Time Complexity Analysis
The table below summarizes the time complexity of each major operation, expressed in Big-O notation and explained in plain terms. N = number of active vehicles, V = intersections, E = road segments, T = simulation ticks.
Operation
Time Complexity
Plain-English Explanation
Dijkstra Routing
O((V + E) log V)
Each of E edges is relaxed once; each relaxation uses a min-heap costing O(log V). V = intersections, E = roads.
Congestion & BPR Update
O(E)
The BPR formula is applied to every road edge exactly once per tick.
Traffic Signal Decision
O(In(j))
Each intersection scans its incoming roads to find the max-queue one. Bounded by max in-degree.
Vehicle Tick Update
O(N)
Each of N active vehicles has remaining_time decremented by 1.
Queue Discharge dij(t)
O(N × In(j))
Computed for each vehicle entering a queue; bounded by intersection in-degree.
Full Simulation Tick
O(T × (E + N))
T ticks total. Routing only fires on segment completion, so BPR update (O(E)) dominates most ticks.
Metrics Aggregation
O(N)
Single pass over all vehicles per tick to accumulate totals.
9.1 Summary
The dominant cost per tick is Dijkstra’s algorithm at O((V + E) log V). However, since rerouting only triggers when a vehicle completes a road segment, the amortized routing cost per tick is much lower in practice. For a typical city graph with V = 50 intersections, E = 150 roads, and N = 200 vehicles, a full simulation of T = 1000 ticks completes in well under one second on modern hardware, enabling smooth real-time Raylib rendering at 60 FPS.
10. Challenges and Solutions
10.1 Graph Construction and Directed Edge Representation
Representing a directed road network with rich per-edge metadata required careful adjacency-list design. This was solved by storing Road objects as shared pointers keyed by (src, dst) pairs, enabling O(1) edge lookup and shared ownership between the graph and signal modules.
10.2 Consistent Tick-Order Updates
Updating vehicle flows, queues, and signals in the wrong order caused vehicles to double-count or appear to teleport. Solved by enforcing a strict five-phase tick order: flow update → congestion recalc → routing → signal update → metrics.
10.3 Stale Entries in Dijkstra’s Priority Queue
Dynamically changing edge weights produced stale priority-queue entries leading to suboptimal paths. Solved using lazy deletion: entries are verified against a visited set and discarded if already settled.
10.4 Raylib Rendering Synchronization
Synchronizing the simulation tick rate with Raylib’s frame rate without blocking the simulation required running the full simulation logic inside the Raylib draw loop with a configurable ticks-per-frame multiplier, decoupling logical speed from visual frame rate.
11. Future Enhancements
Multi-Phase Signals: Extend the signal model to support left-turn and pedestrian phases, approaching real intersection controller behavior.
Reinforcement Learning Signal Control: Replace the max-queue heuristic with a trained DQN agent that directly optimizes the global objective function.
Dynamic Vehicle Generation: Add Poisson-process arrivals to simulate rush-hour demand surges and off-peak quiet periods.
Real Map Data Import: Load arbitrary city maps from OpenStreetMap exports converted to the graph format.
Incident Simulation: Allow mid-simulation road closures or capacity reductions to test rerouting robustness under failure conditions.
Multi-Lane Road Modeling: Extend each edge to carry lane-level flow data for higher-fidelity congestion modeling.
